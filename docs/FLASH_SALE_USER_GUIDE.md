# 抢购用户使用指南

> 更新日期：2026-10-13（上海时间）。面向普通用户和演示参与者，依据当前前后端工作区实现编写；功能已实现不代表已发布到某个线上地址，请使用演示负责人提供的访问地址。
> 这是教学演示系统，支付、退款和用券不涉及真实资金或真实商家履约。本文以后端版本为准，前端保留相同内容的同步副本。

## 1. 先记住这四件事

1. **进入排队、取得订单号，不等于订单已经创建，也不等于付款成功。** 等系统查到订单后再进入支付。
2. **等待 30 秒后停止自动查询，不等于购买失败。** 原请求可能已有订单但尚未确认，请手动查询或查“我的订单”。
3. **网络异常先继续原购买，不要直接再买。** “继续本次购买”复用原请求；“主动再买（新请求）”是另一笔购买，可能形成另一张订单。
4. **取消和退款不同。** 取消待支付订单会释放抢购名额；已支付后的退款不会释放限购名额，也不会回补抢购库存。

## 2. 使用前准备

- 使用正常联网的浏览器，允许网站使用本地存储。系统在发送购买请求前会先保存本次购买记录，存储失败时不会继续提交。
- 登录真实的演示账号。游客可以浏览，但不能购买；升级后的旧登录记录可能需要重新登录。
- 建议只用一个浏览器标签完成购买。不要通过切换账号、清除网站数据、无痕窗口或换设备来“重试”：原购买记录只保存在原浏览器中，不保证跨设备恢复。
- 用原购买账号查看结果和订单。切换账号后不能查询别人的订单；正在操作时账号变化会阻止当前购买/支付流程继续。
- 若购买结果未确认，保留购买请求、订单号和时间，不要清缓存。截图给技术人员前遮挡手机号等个人信息，切勿分享登录 token、密码或验证码。

## 3. 找到正在抢购的商品

从首页进入 **“限时秒杀”** 专区，点击商品卡片打开详情。当前列表只展示本轮正在进行、上架、缓存完整且还有库存的商品；未开始、已结束、售罄、被下架或暂停的商品不会正常展示。

如果页面刚打开时还没开始，开抢后请刷新首页；当前首页不是持续推送库存的实时看板。列表上的库存是查询时的数值，不保证点击时还有货；自己达到限购后也可能继续看到商品卡片。

默认演示数据如下，具体仍以访问环境的实际商品和订单金额为准：

| 商品 | 价格（元） | 初始库存（件） | 每账号每商品限购（件） |
|---|---:|---:|---:|
| 演示抢购·招牌牛肉面 | 1.00 | 10 | 1 |
| 演示抢购·提拉米苏 | 16.80 | 20 | 2 |
| 演示抢购·双人电影票 | 19.90 | 30 | 2 |

默认每次后端启动追加一轮新商品，在本轮数据生成约 60 秒后开抢，持续 30 分钟；不是每小时自动清空重置。商品 ID 会变化，旧链接可能不能再次购买，但历史订单保留。

详情页部分原价、门店数量、使用规则、地址及套餐装饰内容仍有原型展示，不能当作真实商业承诺。**支付页从真实订单读取的金额与状态才是本次交易依据。** 一次点击买一件，不支持在同一订单增加数量。

## 4. 第一次抢购：按这条路径操作

**登录 → 首页限时秒杀 → 商品详情 → 购买进度 → 真实订单支付页 → 模拟支付 → 我的订单**

### 第一步：查看商品并提交

1. 打开商品详情，等待商品数据加载完成，再点底部购买按钮。
2. 未达到限购且无历史购买记录时，点击“立即购买”或“立即下单购买”提交第一次购买。两个按钮不是购买不同数量，实际金额以真实订单为准。
3. 系统先在浏览器保存购买请求标识，再向服务端提交；受理后进入“秒杀购买进度”页。
4. 如果出现“已达购买上限”，按钮会灰显，点击只显示“限购【N】件，您已达到购买上限”，不会发出新购买请求。这里 N 是该商品实际限购数量。

### 第二步：等待建单

购买进度页会显示购买请求、取得的订单号、受理时间和自动查询截止时间（上海时间）。系统通常每秒查询一次，到服务端返回的截止时间停止自动查询。

| 页面显示/操作 | 应如何理解 |
|---|---|
| 正在等待建单 | 已受理并正在查询，不是订单已经创建 |
| 购买结果尚未确认 | 暂时无法确认，可能是网络异常，不代表失败 |
| 已停止自动查询 | 自动等待已截止，不代表原请求已安全结束 |
| 手动查询结果 | 已有订单号时继续查原请求的建单结果 |
| 重试本次购买（同一请求键） | 未取得订单号时用原购买标识重试，不创建新的购买意图 |
| 查看我的订单 | 查询当前账号已经创建的订单，不会显示尚未建单的排队请求 |

查到订单后会进入支付页。即使刚查到订单，它也可能已经支付、取消或退款；以支付页重新查询的状态为准。

### 第三步：确认并支付

1. 核对真实订单号、商品、金额及状态。
2. 仅待支付且未超过截止时间的订单可以点“去支付”。默认支付期限从建单起 15 分钟，具体以页面的支付截止时间为准。
3. 支付为教学模拟，不会打开真实银行或第三方支付。成功后订单为“待使用”，系统生成券码并进入成功页。
4. 如果显示“支付结果未确认”，先点 **“刷新订单状态”**。网络失败不证明支付失败，当前支付流程不会因失败直接跳成功页。
5. 倒计时结束后不能付款，即使超时取消任务尚未把状态改为已取消。刷新不会重置支付期限。

## 5. 继续本次购买，还是主动再买？

| 操作 | 适合的情况 | 结果与风险 |
|---|---|---|
| 继续本次购买/同一请求键重试 | 刷新、断网、未收到响应、希望查原结果 | 复用已保存的原请求标识，不延长排队期限、不再次预占 |
| 手动查询结果 | 已有订单号，自动查询已停止或暂时异常 | 只查原订单是否创建，不重新下单 |
| 主动再买（新请求） | 确实希望再买一件，且愿意承担原请求仍可能有订单的风险 | 使用新请求标识，可能生成另一笔订单；仍受库存与限购约束 |

详情页恢复购买记录后会显示“继续本次购买”和“主动再买（新请求）”。主动再买会提示原请求仍可能生成订单，需要确认后才提交；从进度页点再买会先回到详情，不表示已经买成功。

建议先查原请求及我的订单，再决定是否再买。不要把“尚未查到订单”“停止自动查询”理解成可以安全重复购买。原请求已终止后，复用原键也不会开启新的抢购；真正的新购买需要主动再买的新请求。

如果个人额度已满，详情页不会允许新购买，甚至可能无法从该页继续进入原排队记录；请使用已打开的购买进度页、原进度链接或“我的订单”查结果，不要试图绕过限购。

## 6. 取消、退款和用券

### 取消待支付订单

在真实订单支付页点击 **“取消订单”**，确认后刷新查看状态。只有待支付订单能取消，取消与支付同时发生时以服务端最终状态为准。

取消成功会回补库存并释放一个限购名额。但商品必须仍属于本轮、在活动时间内且上架可用，才可能恢复展示和购买。活动已结束或系统异常时，不保证取消后立刻能再买。

排队请求还没建单时，没有独立的“取消排队”按钮或接口。关闭页面不会取消原请求，也不证明额度已释放。

### 退款与去使用

支付后的订单可从个人中心待使用订单进入券页。后端仅允许待使用订单退款；到期前可以执行本人“去使用”，使用后不能再按待使用订单退款。券有效期由实际支付时间和商品有效天数决定，默认演示商品为 30 天，不是排队时间起算。

**当前券页的提示存在演示边界：** “在线点单”会调用教学核销接口；核销接口失败时页面仍可能显示成功，退款失败时也可能提示模拟成功。“再来一单”、客服、地图等部分按钮仍是原型。不要仅凭这些提示认定订单已经使用或退款；返回并重新查询真实订单，存在疑问时让技术人员按订单号核对。页面“原路退回”文案不代表发生真实资金退款。

退款（包括券到期自动退款）**不释放限购、不回补库存**。已退款订单仍计入该商品的购买额度；取消待支付订单才可能释放名额。自动退款由后台扫描执行，不承诺到期瞬间页面立即更新。

## 7. 常见情况及处理

| 情况 | 建议操作 |
|---|---|
| 首页没有抢购商品 | 确认是否开抢，刷新首页；也可能已结束/售罄/下架/暂停，联系演示负责人核对 |
| 商品卡片可见，点击时已抢光 | 列表是快照；不要反复新建请求，已有购买记录仍查原结果 |
| 尚未支付，却提示限购 | 排队预占和待支付订单也占额度；先查购买进度和我的订单 |
| 已取消但还不能买 | 刷新详情；可能活动结束、商品暂停/下架或缓存回补待核对，不保证立即恢复 |
| 已退款却仍提示限购 | 符合规则，退款不释放该商品的购买名额 |
| 等待超过 30 秒 | 手动查原结果、查我的订单；仍不明时提供订单号/请求标识给技术人员 |
| 提交后断网或刷新 | 原账号、原浏览器继续本次购买；不要清除本地记录或直接主动再买 |
| 本地购买记录无法读取 | 恢复浏览器存储，先查我的订单；不要清空后立即重买 |
| 重新登录或换账号后找不到结果 | 登录原购买账号；换设备不保证恢复本地请求记录，已创建订单可用原账号查 |
| 重启后旧商品不能买 | 每次启动是新轮，新商品有新 ID；回首页看本轮商品，已建历史订单按原期限/状态处理 |
| 支付倒计时结束但仍待支付 | 已不可支付，刷新等待取消状态；后台任务有执行延迟 |
| 核销/退款显示成功但订单未改变 | 券页保留模拟兜底，不能只看提示；刷新订单并联系技术人员核对 |

## 8. 联系技术人员时提供什么？

提供访问环境、商品名称/ID、订单号（如有）、购买请求标识、受理/异常时间、页面提示及脱敏截图。明确说明是否刷新、断网、切换账号、点击主动再买或清除过网站数据。

不要提供 token、密码、验证码或完整个人信息。技术人员应结合本人订单查询、Redis 请求及日志核对；结果不明时不应要求用户通过频繁再买验证。系统尚无普通用户可操作的自动恢复或对账平台。
