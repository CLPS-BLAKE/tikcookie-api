## 2. 配置清单

所有地址、账号和密钥由受控环境文件或环境变量注入，示例只放占位值。`DSS_` 是后端配置前缀。四种中间件均连接 node1 的可达私网地址/受控入口，实际端口以部署记录为准。实例名 node1 不保证 DNS 可解析；应用容器的 localhost 也不自动指向宿主机中间件。

本地开发时 `application.yml` 里有 `spring.config.import: optional:file:./.env[.properties]`：把 `.env.example` 复制成 `tikcookie-api/.env` 填好，IDEA 直接点 Run 或命令行 `mvn spring-boot:run`（工作目录为 `tikcookie-api`）都会自动读到，不需要再往运行配置里逐项粘环境变量。文件不存在时这行不生效，服务器仍按环境变量注入；操作系统环境变量的优先级高于 `.env`，所以生产上即使误放了 `.env` 也不会盖掉真实配置。`.env` 已在 `.gitignore`，不要提交。

## 3. MySQL 与 MyBatis-Plus

### 3.1 数据规则

- 数据库 `dss`，字符集 `utf8mb4`，所有表 InnoDB。五张表：`users`、`shops`、`products`、`orders`、`favorites`。本期**没有** `outbox_events` 表。
- 所有主键 `BIGINT AUTO_INCREMENT`，Java 用 `Long`，对外 JSON 统一字符串。金额用 `BIGINT` 分。店铺图片、套餐内容和使用规则用 JSON 列；MyBatis-Plus 的 JSON TypeHandler 映射实体，服务层检查数组元素结构。
- 普通商品 `stock = NULL`；抢购商品 `stock` 为 MySQL 权威库存。订单保存购买时商品名、店名、图片 ObjectKey、金额快照，避免之后商品修改影响历史订单。
- 应用账号只需对 `dss` 的 SELECT/INSERT/UPDATE/DELETE 权限。建表由单独管理账号执行。脚本只针对空库，不是 MongoDB 数据自动迁移或已有 MySQL 表结构的升级脚本；部署前备份旧数据。

### 3.3 最小事务实现

- `@Transactional` 用在订单创建、支付、取消、退款和核销。支付/退款/取消/核销都只在订单原状态符合时更新；更新行数不为 1 即拒绝或忽略重复处理。同一事务完成订单与销量/库存变化。券码唯一性由 `uk_voucher_code` 兜底；若撞号，回滚并在**新事务**重试。
- 抢购下单在短事务内读取并锁定商品行（`SELECT ... FOR UPDATE`），检查上架、时间窗、剩余库存及该用户未取消订单数；扣一件库存，插入订单。取消抢购单按同一商品行顺序锁定，订单确为 `UNPAID` 才回补库存。此处只是最小正确性保护，不引入 Redis Lua、分布式锁或压力测试目标。
- 每分钟扫描 `UNPAID AND pay_deadline <= NOW(3)` 作超时取消；每分钟扫描 `UNUSED AND expires_at <= NOW(3)` 作到期退款。单实例运行，无需 Redis 任务锁。每批数量可限制；扫描任务与用户操作复用同一事务方法，重复处理不能重复加减。
- 当前到期退款更新错误地用 `expires_at > expiredBefore`，与扫描条件相反；需修复并验证未到期不退、到期可退、重复扫描不重复扣销量，不能仅启用任务就认为功能可用。
- 需要自定义 SQL 实现商品行锁、条件状态更新和库存修改；MyBatis-Plus `BaseMapper` 用于普通 CRUD 和分页。应用不再依赖 Mongo Repository、MongoTemplate、MongoDB URI 或 Mongo 事务。

## 4. Redis

Redis 只存短期登录数据，丢失后用户重新登录；订单与库存不会丢失。统一 `dss:` 前缀，使用 `StringRedisTemplate`。

| key | TTL | 值和用途 |
|---|---|---|
| `dss:login:code:{phone}` | 5 分钟 | 6 位验证码；重发覆盖 |
| `dss:login:code:interval:{phone}` | 60 秒 | 发送间隔标记 |
| `dss:login:code:fail:{phone}` | 5 分钟 | 累计错误次数；第 5 次按接口码失效 |
| `dss:login:token:{token}` | 7 天，访问续期 | 用户 ID、昵称、头像等登录信息 |

验证码只在开发/受控演示日志中出现，不经外部短信网关。数据库 ID、抢购库存、已购计数都不放 Redis。本期不做热门商品缓存和多实例任务锁。Redis 账号或口令仅私网和环境变量配置。

## 5. Logstash、RabbitMQ 与 ES

截至 2026-10-08：负责人确认 **Logstash 已部署并完成 MySQL → ES 同步**，部署目录 `/opt/tikcookie-data`。`dss_shop` 已有 5 条、`dss_product` 已有 30 条，与 MySQL 核对一致，mapping 符合配置。命令证据及维护说明见 [Logstash 部署记录](LOGSTASH_SYNC.md)。Java `SearchService` 查询、sync 和 rebuildAll 仍是桩；数据同步成功不表示搜索 API 或 RabbitMQ 消费链路已完成。

### 5.0 当前采用的 Logstash JDBC 同步

每分钟读取 `shops` 和 `products JOIN shops`，首次无游标时全量导入，之后按更新时间覆盖同一主键文档。商品跟踪 `GREATEST(p.updated_at, s.updated_at)`，店铺改名/分类会触发关联商品刷新；两个独立游标、持久队列使用 `logstash_data`。交付配置是 Logstash 8.19.22 + Connector/J 8.4.0，实机版本/摘要尚待登记。

当前同步不依赖 RabbitMQ；既有发布器/消费者代码保留，未实现消费可能进入失败流程，仍需检查消息和死信。未来启用 Java/MQ 写入前先明确写入方切换，避免与 Logstash 相互覆盖。

数据库变更必须维护 `updated_at`；查询有 5 分钟回读窗口及 10 秒延迟，不能保证强一致或任意长事务零漏读。物理 DELETE 不自动删除 ES 文档；错误 mapping、删除残留需备份后单独处理。保持 `DSS_SEARCH_REBUILD_ON_STARTUP=false`，不调用未实现的 Java 重建入口。交付 Logstash 内存限额 768 MiB、堆 256 MiB，应计入 2C4G 主机资源预算。

### 5.1 既有 RabbitMQ 消息拓扑（消费同步未完成）

RabbitMQ 建 vhost `/dss`、专用应用账号、持久化队列。后端数据库事务提交后发消息；只需要如下最小拓扑：

| 名称 | 类型 / 绑定 | 用途 |
|---|---|---|
| `dss.search.direct` | direct 交换机 | 发送 `shop.changed`、`product.changed` |
| `dss.search.sync` | 持久化队列，绑定上述两个 routing key | 单消费者顺序处理（并发数 1） |
| `dss.search.dlx`、`dss.search.dlq` | 失败交换机与持久化死信队列 | 处理失败时暂存，供组员检查 |

消息体示例：`{"type":"PRODUCT","id":"123"}`；店铺用 `SHOP`。原 MQ 目标是消费者回查 MySQL 当前记录并覆盖 ES，店铺变化时刷新关联商品；写 ES 成功后确认，失败进死信。发布与入口已有，但 `sync` 未实现，不作为当前同步路径，也不把未实现的 `rebuildAll` 写成恢复步骤。当前使用 Logstash 轮询及维护重放；MQ 生产/消费/失败处理仍单独验收。**不要把消费者读到的消息当作订单写入依据。**

### 5.2 索引定义和查询

`dss_shop` 和 `dss_product` 两个索引已创建，mapping 已核对；由 Logstash 管理模板并写入。字段与 API VO 不必相同，后续 Java 查询返回时映射为 `ShopHitVO`、`ProductHitVO`。使用 ES 内置分析器，无需安装 IK 插件；下表查询规则仍待 Java 搜索实现。

| 索引 | 必需字段（类型） | 查询规则 |
|---|---|---|
| `dss_shop` | `id` keyword、`name` text、`address` text、`category` keyword、`cover` keyword、`businessHours` keyword、`createdAt` date | 关键词查店名/地址，分类过滤；无关键词按创建时间倒序 |
| `dss_product` | `id` keyword、`shopId` keyword、`name` text、`contentsText` text、`shopName` text、`shopCategory` keyword、`type` keyword、`status` keyword、`price` long、`soldCount` integer、`image` keyword、`flashStartTime`/`flashEndTime` date | 仅上架；关键词查名称、内容、店名；分类/类型过滤；按接口约定综合、销量、价格排序 |

`contentsText` 从 MySQL `contents` 中抽取条目名称组成；`image`/`cover` 仍存 OSS ObjectKey，响应 URL 用配置的图片前缀拼装。`createdAt` 和抢购时间的索引格式需与应用统一。`status=OFF_SHELF` 时仍可保留文档，但搜索必须过滤它。商品详情和剩余库存始终从 MySQL 查询，不以 ES 数据作为最终值。

首次导入已确认成功。后续恢复可在停机维护窗口重置 Logstash JDBC 游标或临时启用 `clean_run` 全量覆盖，不能清除物理删除残留或修复已有错误 mapping；清空/重建索引需单独备份维护。Java `rebuildAll` 仍未实现，不新增公开维护 API。ES 查询失败按原接口文档返回 `107001`（查询实现待完成）；中文词组、排序及页面搜索仍需联调，增量/关联变更和重启恢复补录逐项证据。

  写入只用后端自己的 RAM 身份（或专用最小权限 RAM 用户），**不向前端发长期 AccessKey**。
  公共读下拿到 `fileId` 的人都能看图，所以只放可公开展示的头像/商品图。
- 图片读取默认**前端直连 OSS**：上传接口返回的 `url` 是 OSS 公共域名（`https://{bucket}.{endpoint-host}/{fileId}`），
  游客和登录用户都能直接放进 `<img src>`，不占后端带宽，也不需要 token。
  `DSS_FILE_BASE_URL` 填这个公共域名（或自己的 CNAME 域名）；**留空时由 `FileUrlResolver` 自动推导**，少配一个变量。
- 后端仍保留公开的**代理读图接口** `GET /api/v1/images/{fileId}`：用后端凭据从 OSS 取流，按对象里存的
  Content-Type 写给浏览器，并带 `Cache-Control: public, max-age=31536000, immutable` 和 ETag
  （命中 `If-None-Match` 返回 304）。Bucket 若收紧为私有读，把 `DSS_FILE_BASE_URL` 改回后端读图接口
  （本地 `http://127.0.0.1:8080/api/v1/images`，服务器 `https://<演示域名>/api/v1/images`）即可，前端不用改。
- 上传接口先校验文件非空、扩展名及实际内容类型（jpg/png/webp），单文件 5 MB；生成随机 ObjectKey，形式为
  `group1/M00/00/00/{32 位十六进制随机名}.{jpg|png|webp}`（路径形式沿用接口示例的历史 FastDFS 风格，不部署 FastDFS；
  由 `com.dss.common.file.ObjectKeys` 生成，前缀常量不带结尾斜杠），通过 OSS SDK 上传。数据库保存 ObjectKey；
  `fileId` 返回该 key，`url` 返回 `图片公共前缀/{fileId}`。任何既有 `fileId` 只作为标识，
  不作为前端可构造的密钥或本地路径。
- 应用只接受本服务上传的对象 key，禁止用户传入任意 URL 指向外部资源。对象上传成功但数据库写入失败时，
  教学版允许留少量孤立文件，部署人员定期清理。
- 读图接口是公开的（`<img src>` 带不了 Authorization 头），安全性依赖两点：ObjectKey 是 32 位随机十六进制、
  不可枚举；图片本身就是可公开展示的头像/商品图。**公共读下"不可枚举"是唯一屏障**，
  所以敏感图片不能放这个 Bucket。若以后要放敏感图片，需要改成签名 URL 或加鉴权，属于下一版范围。
- 代理读图会占用后端带宽和连接（默认不走它，只作备用）；若要抗量，可在后端前面挂 CDN 并让 CDN 回源到这个读图接口。
- `<img src>` 不受 CORS 限制；若要允许前端用 `fetch` / WebGL 读像素，在 Bucket 上配置 CORS 规则放行前端域名即可。

## 7. Nginx、Swagger 与访问边界

目标由 Nginx 以 `/` 提供 Vue 构建物，`/api/` 转发 Spring Boot 并保留 `/api/v1` 原路径。以下仅是 Nginx 与后端同机、非隔离容器网络时的示例，不表示应用已驻 node1；若分机/容器运行，proxy_pass 必须改为实际受控后端地址：

```nginx
server {
    listen 80;
    server_name _;
    root /srv/tikcookie-web/dist;
    index index.html;

    location ^~ /api/v1/internal/ { return 403; }
    location ^~ /swagger-ui { return 403; }
    location ^~ /v3/api-docs { return 403; }
    location /api/ { proxy_pass http://127.0.0.1:8080; }
    location / { try_files $uri $uri/ /index.html; }
}
```

Swagger UI (`/swagger-ui.html`) 和 OpenAPI 描述 (`/v3/api-docs`) 不经 Nginx 对外转发；后端 8080 只给受控来源访问。组员通过受控方式使用 Swagger 并带 `X-Internal-Key` 操作内部接口。生产演示域名配置 HTTPS 后再开放到公网。图片 URL 指向 OSS，不通过 Nginx 代理。CORS 由 Nginx 同源入口解决。
