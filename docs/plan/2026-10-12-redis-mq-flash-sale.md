## 一、范围与约束

### 本次实现

- 每次启动追加本轮演示抢购商品。
- 上一轮商品下架，商品及历史订单全部保留。
- 本轮商品提前缓存，到时上架、结束下架。
- 抢购开始后冻结全部商品资料，上下架及交易更新除外。
- Redis 商品列表、详情、库存和限购。
- Lua 原子预占、请求去重、幂等释放。
- MQ 异步建单，30 秒排队期限。
- 雪花订单号，全链路复用现有 `orders.id`。
- 直接查询 MySQL 获取建单结果。
- 模拟支付、取消、使用、退款。
- MQ 支付超时通知及数据库扫描兜底。
- 必要的失败补偿和迟到消息拒绝。

### 明确不实现

- 活动模型、活动表。
- `flash_request_id` 或其他新增数据库字段。
- 请求表、额度表、Outbox。
- Redis 抢购结果缓存、WebSocket。
- 自动异常重试、死信管理或恢复平台。
- 用户限流、MQ 积压保护、验证码、反作弊。
- 真实支付。
- 多实例同时播种、跨服务无损恢复。

**数据库结构不新增表、字段或索引。**现有表主键、历史数据保留，调整的是应用中的订单 ID 生成和业务逻辑。

## 二、最终业务规则

### 1. 启动与演示数据

```text
关闭新请求受理，建单消费者暂不启动
    ↓
识别上一轮演示商品，统一下架
    ↓
处理上一轮未建单预占
    ↓
追加本轮商品，使用新的商品 ID
    ↓
初始化本轮 Redis 数据
    ↓
启用消费者、订单任务与商品调度
    ↓
到达开抢时间且缓存就绪，本轮商品上架
```

- 商品使用数据库原有自增机制追加，不复用固定商品 ID。
- 演示店铺可以复用脚本管理的专用店铺，不必每轮新建。
- 通过演示专用店铺范围识别演示商品；不得把全库 `FLASH` 商品一律下架。
- 不删除商品、订单、评价、收藏或用户。
- 旧订单保留原支付截止时间和券有效期。
- 不清空整个 Redis、MQ 队列或数据库。

脚本以同一个初始化时间为基准：

```text
开抢时间 = 初始化时间 + 脚本中的时间偏移
结束时间 = 开抢时间 + 脚本中的持续时间
```

时间偏移只在演示脚本中定义，不增加创建接口的固定缓冲配置。

复用的是演示分支中“启动执行 classpath SQL”的方式，而不是“存在标记商品就跳过”或删除固定 ID 范围的旧行为。也不继续使用每小时破坏性重置方式管理本方案的演示数据。

### 2. 商品展示与上下架

| 情况 | Redis 列表与抢购行为 |
|---|---|
| 本轮未开始 | 不展示、不接受抢购 |
| 到达开始时间且缓存就绪 | 首次自动上架 |
| 本轮上架、时间窗内、库存大于 0 | 展示，允许抢购 |
| Redis 库存为 0 | 隐藏，禁止新抢购，不主动修改上下架状态 |
| 本轮回补后库存大于 0 | 仍在时间窗内且上架时，恢复展示 |
| 手动下架 | 隐藏、禁止新抢购 |
| 结束时间到达 | 自动下架，保留商品和订单 |
| 上一轮商品回补库存 | 不恢复展示、不恢复抢购 |

**首次自动上架只执行一次。**定时扫描不能把用户已经手动下架的商品反复重新上架。

继续复用 `ON_SHELF / OFF_SHELF`，不扩展商品状态枚举。手动上架不能绕过本轮资格、时间窗和缓存就绪条件。

### 3. 冻结规则

仅针对 `FLASH`：

- 开抢前允许修改商品资料。
- 达到开抢时间后，禁止人工修改全部商品资料。
- 冻结范围包括名称、图片、价格、套餐、规则、有效期、库存配置、限购和时间窗。
- 上下架仍允许，但不能绕过时间窗或恢复上一轮商品。
- 正常库存扣减、取消回补、销量更新不属于人工编辑。

普通商品沿用原有规则。

### 4. 请求和限购

- 一次请求购买 1 件。
- 主动再次购买使用新幂等标识。
- 同一次购买重试复用原标识，不再次预扣。
- 限购包含排队预占，以及待支付、待使用、已使用、已退款订单。
- 建单失败、未支付取消释放额度。
- 退款不释放额度。
- 从首次预占成功起，最多排队 30 秒；重试不延期。
- 实际建单时重新检查商品状态、时间窗、本轮资格和请求期限。
- 本轮请求排队期间商品下架或活动结束，未建单请求失败并安全释放预占；已提交的订单不撤销。

## 三、订单号与接口契约

### 1. 雪花订单号

所有新订单统一通过同一个后端雪花生成器发号：

- 普通订单：同步建单时生成。
- 抢购订单：Redis 预占前生成候选订单号。
- Redis 去重命中时，返回原绑定订单号，丢弃新生成的候选号。
- MQ 消息、数据库订单、补偿和结果查询复用该订单号。
- 历史订单号不修改。
- HTTP 中订单号始终使用字符串。

可复用 MyBatis-Plus 的 `IdentifierGenerator` 接入雪花生成，订单实体采用相应的应用发号策略，不再依赖插入后获取自增 ID。

实现时检查固定节点参数、时钟回拨和重启行为；发号异常停止该请求，不伪造或随意回退订单号。保持数据库现有表结构，避免在应用中继续混用普通订单自增与抢购订单应用发号两套策略。

### 2. 现有抢购提交接口

保留：

```http
POST /api/v1/orders/flash
```

新请求体：

```json
{
  "productId": "商品ID",
  "requestKey": "本次购买的幂等标识"
}
```

受理响应：

```json
{
  "orderId": "雪花订单号",
  "state": "PROCESSING",
  "acceptedAt": "首次预占时间",
  "queueDeadline": "首次预占时间加30秒"
}
```

示例展示的是响应 `data` 内容，保留项目现有统一 `Result` 外层包装。

`requestKey` 只用于 Redis 去重，不进入数据库。前端为每次新的购买意图生成标识，并在发送前保存；主动再次购买生成新标识，网络重试保留原标识。相同标识不能改绑商品或用户。

**拿到订单号不等于订单已创建。**MQ 投递结果不确定时，不能响应“已经失败并释放”，必须保留原请求关联。

### 3. 新增一个建单结果接口

建议路径：

```http
GET /api/v1/orders/flash/result/{orderId}
```

只查询：

```text
orders.id = orderId
且 orders.user_id = 当前登录用户
```

查到订单：

```json
{
  "state": "CREATED",
  "orderId": "雪花订单号",
  "orderStatus": "UNPAID"
}
```

未查到订单：

```json
{
  "state": "NOT_CREATED"
}
```

该接口：

- 不读 Redis 结果缓存。
- 不增加请求表。
- 不声称能够给出准确的异步失败原因。
- 不泄露其他用户订单。

前端根据提交响应中的期限停止轮询，但一次 `NOT_CREATED` 或网络超时不能直接证明请求已经被安全终止。

### 4. 商品查询

| 接口 | 改造 |
|---|---|
| `GET /api/v1/products/flash` | 从 Redis 读取可展示商品 |
| `GET /api/v1/products/{productId}` | 抢购详情读 Redis，普通商品详情维持原逻辑 |
| 普通下单、支付、取消、退款、使用接口 | 保留 URL |

抢购详情需要可用的商品类型索引或路由识别，**不能在抢购缓存缺失时误走普通商品的 MySQL 回源路径**。

前端仍通过后端 HTTP API 访问数据，不直接连接 Redis。抢购商品不经过 Elasticsearch。

## 四、Redis 数据设计

首版使用单实例 Redis，不增加 Cluster 适配范围。

| 数据 | 职责 |
|---|---|
| 本轮商品集合 | 判断是否属于本轮、控制上架和新请求准入 |
| 可展示商品索引 | 列表排序与商品成员维护 |
| 商品资料缓存 | 名称、价格、图片、店铺、状态、时间和限购 |
| 商品库存 | Redis 可预占库存 |
| 用户额度 | 排队及已建单的占用数量 |
| 请求记录 | 用户、商品、订单号、首次预占时间、截止时间、释放标记 |
| 待到期请求索引 | 触发 30 秒未建单请求终止 |

请求记录只服务于去重和补偿，**不是前端查询的结果缓存**。

展示库存为 Redis 中可以接受新请求的库存；MySQL 库存为已完成建单扣减后的库存。排队期间允许二者暂时不同。

### Lua 操作

1. **预占**
   - 校验缓存完整、本轮资格、状态和时间。
   - 相同请求优先返回原绑定。
   - 检查库存和额度。
   - 扣库存、占额度、保存请求、加入到期索引。
   - 库存变为 0 时移出展示索引。

2. **确认建单**
   - 保留占用，不再次扣 Redis 库存。
   - 移出未建单到期索引。
   - 记录补偿所需的建单状态。

3. **终止与释放**
   - 检查是否已释放。
   - 仅一次回补库存和额度。
   - 仅本轮、上架、时间窗内商品恢复展示。
   - 保留终止标记，拒绝迟到消息。

Lua 用于原子完成这些检查和修改，禁止脚本内全量扫描请求。执行前检查必要字段和数据类型，不能把脚本原子执行误认为具有数据库事务回滚能力。

交易记录不能简单设置为“30 秒后自动删除”。排队到期必须执行终止和补偿；终止标记也不能立即删除，否则迟到消息可能被误认为新请求。

### 缓存维护与故障规则

- 商品资料、库存、限购分开维护。
- 刷新资料、上下架、恢复展示不重置库存和额度。
- 启动只初始化本轮新增商品，不覆盖旧轮交易计数。
- 商品或库存缓存缺失时，不展示、不受理；不在请求中查询 MySQL/ES 自动重建库存。
- Redis 不可用时暂停抢购，不切回旧 MySQL 同步抢购。
- 不确定的 Redis 操作不能盲目再次预扣或释放。
- 严重数据丢失允许人工恢复或重启追加新一轮；历史数据库记录保留，不承诺无损自动恢复。

## 五、MQ、事务与补偿设计

### 1. MQ 拓扑

首版只需要：

```text
建单交换机 → 建单队列

支付超时等待队列
    ↓ TTL 到期后的死信路由
支付超时执行队列
```

- 建单队列不配置自动异常重试。
- 不建立业务失败死信处理平台。
- 消费者使用独立的配置，不继承当前全局自动重试行为。
- 超时队列的死信路由是延时机制，不是异常恢复平台。
- 不改动原搜索链路。
- MQ 发布处理 confirm 与 return；确认接收不等于订单已经创建。

### 2. 建单事务

消费者按以下顺序执行：

```text
取得商品处理协调锁
    ↓
核对订单是否已经存在
    ↓
检查请求有效且未终止
    ↓
检查本轮资格和30秒期限
    ↓
开启 MySQL 事务，锁商品行
    ↓
校验上架、时间、限购和库存
    ↓
扣减 MySQL 库存
    ↓
以原 orderId 创建 UNPAID 订单
    ↓
提交前再次核对请求期限
    ↓
提交事务
    ↓
确认 Redis 预占，发送支付超时消息
    ↓
确认 MQ 消息
```

重复消息如果已经存在订单，不再扣库存。

消费者确认必须在数据库提交之后；发布确认与消费确认是独立机制，连接中断仍可能造成重投，不能把“不配置重试”等同于“绝不重复投递”。

### 3. 建单与终止的协调

这是首版必须落实的技术点：

- 建单、30 秒终止、失败补偿及取消回补使用同一套商品处理协调机制。
- 首版可使用单 JVM、按商品组织的锁，不引入分布式锁框架。
- **锁必须覆盖数据库事务提交完成**，不能方法返回前释放、事务却尚未提交。
- 消费者先取得协调锁，再进入事务，避免旧查询快照影响判断。
- 请求终止后，迟到消息检查到终止状态，不允许建单。
- 已提交订单不能被当作失败请求补偿。

这也是本方案明确限定单实例的原因，不把它描述成多实例一致性方案。

### 4. 异常丢弃规则

| 情况 | 处理 |
|---|---|
| 确定业务失败且没有订单 | 终止请求、幂等释放，丢弃消息 |
| 已有订单 | 保留订单，不回补预占 |
| MQ 发送失败且确定未投递 | 安全终止、释放 |
| 发送或数据库提交结果不确定 | 核对；不能盲目释放 |
| Redis/数据库无法核对 | 停止该商品受理，保留不确定状态，允许人工恢复 |
| 迟到、重复、旧轮建单消息 | 按订单和终止状态处理，不重新预占 |

不自动重新发布失败消息，不建设恢复平台。必要的到期终止和补偿仍保留，避免“直接丢弃”造成正常演示中永久占用库存。

## 六、订单生命周期接入

### 支付

- `UNPAID → UNUSED`。
- 获取必要锁后，重新检查支付截止时间。
- 默认截止时间为订单创建时间 +15 分钟。
- 复用 `MockPayService`、券码及销量逻辑。
- 不重复扣 Redis 或 MySQL 库存。

### 取消

主动取消、MQ 超时、扫描兜底共用：

```text
订单 UNPAID → CANCELLED
MySQL 库存 +1
事务提交后，幂等回补 Redis 库存和额度
```

只在订单状态迁移成功后回补。

如果数据库已取消而 Redis 更新失败，不能报告为“数据库取消未发生”或再次增加 MySQL 库存；保持商品暂停，按已确认的简化故障边界处理。

### 退款和使用

- 退款不回库存、不释放限购。
- 使用不改变库存或限购。
- 修复现有到期退款条件错误。
- 旧轮订单继续处理，但不会使旧商品恢复展示。
- 旧商品交易缓存存在时执行幂等更新；缺失时不能新建可售缓存或恢复旧轮商品。

### 支付超时

MQ 等待队列使用 15 分钟 TTL；消费时再次检查 `status` 和 `payDeadline`。

TTL 不是精确业务定时器，消息到达可能晚于截止时间，所以支付接口自身必须拒绝过期支付，数据库扫描继续兜底。

## 八、分阶段工程任务与验收

每阶段采用“失败测试 → 最小实现 → 验证 → 独立提交”的顺序。测试先使用 Mock 和可控时钟，集成测试仅连接隔离环境。

### 阶段 1：订单号与现有交易正确性

- [ ] 接入统一雪花生成器，提前生成抢购订单号。
- [ ] 普通订单使用同一生成器。
- [ ] 保留历史订单和现有数据库结构。
- [ ] 修复到期退款比较条件。
- [ ] 修复抢购资料编辑覆盖库存的风险。
- [ ] 加入开抢后全资料冻结。

**验收用例**

- 普通订单仍同步创建。
- 显式指定的抢购订单号不会被 ORM 改写。
- 重复订单号不造成第二次库存扣减。
- 普通商品可编辑，开抢后的抢购商品不可编辑。
- 到期退款成功，库存和限购不回补。

### 阶段 2：启动追加与本轮隔离

- [ ] 引入启动执行追加 SQL 的流程。
- [ ] 下架旧演示商品，不删除记录。
- [ ] 插入新商品，回读本轮商品 ID。
- [ ] 预热缓存之前保持新请求和建单消费关闭。
- [ ] 终止旧轮未建单请求，保留已有订单。
- [ ] 移除演示场景对每小时破坏性重置的依赖。

**验收用例**

- 连续启动两次，商品数量增加，旧记录仍在。
- 旧商品状态下架，新商品使用新 ID。
- 旧订单截止时间和有效期不变。
- 无关商品、用户、订单和收藏不变。
- 初始化失败时不开放半初始化商品抢购。

### 阶段 3：缓存、冻结和上下架

- [ ] 建立本轮集合、展示索引和资料缓存。
- [ ] 库存、额度与资料独立维护。
- [ ] 商品列表、抢购详情读取 Redis。
- [ ] 首次到时上架、结束下架。
- [ ] 手动上下架同步数据库及缓存。
- [ ] 缺缓存或 Redis 异常时停止受理。

**验收用例**

- 未开始商品不展示。
- 售罄隐藏，不主动下架。
- 人工下架后不会被定时器反复上架。
- 上下架不重置库存、限购。
- 冷缓存不自动绕过 Redis 查询库存继续售卖。
- 结束和旧轮商品不能恢复。

### 阶段 4：Lua 预占与幂等绑定

- [ ] 实现预占、确认、终止、释放脚本。
- [ ] 首次请求绑定用户、商品、请求键和订单号。
- [ ] 重复请求返回原订单号及原期限。
- [ ] 原子处理售罄移出索引、回补恢复索引。
- [ ] 建立 30 秒待到期索引。

**验收用例**

- 库存 10，20 个不同请求并发，最多预占 10 件。
- 限购 2，同一用户多个并发请求最多占用 2 个名额。
- 相同请求键重复提交，只占一次库存。
- 重试不更新首次受理时间。
- 重复释放只回补一次。
- 相同请求不能改绑商品或用户。

### 阶段 5：MQ 建单与30秒终止

- [ ] 创建独立 MQ 拓扑、发布和消费者配置。
- [ ] 关闭该消费者的自动异常重试。
- [ ] 建单事务复用 MySQL 库存、限购及快照逻辑。
- [ ] 接入协调锁，覆盖完整事务提交。
- [ ] 实现超时、旧轮、下架和结束请求拒绝。
- [ ] 实现安全补偿和异常消息丢弃。
- [ ] 旧同步抢购入口改接新受理服务。

**验收用例**

- 同一消息多次投递，只创建一笔订单。
- 建单与补偿竞争，不出现订单存在却库存已释放。
- 超过 30 秒的迟到消息不建单。
- 建单成功、Redis 后续操作失败时不误回补。
- 服务重启后旧轮未建单消息被拒绝。
- 正常订单超时消息不因重启被整体清空。

### 阶段 6：支付、取消、退款和兜底

- [ ] 建单后发送支付超时消息。
- [ ] 主动取消、超时消费、扫描共用事务逻辑。
- [ ] 接入 Redis 库存、限购的一次性回补。
- [ ] 支付取得必要锁后重新校验截止时间。
- [ ] 保持退款、使用规则。
- [ ] 正确处理旧轮订单及缺失旧缓存。

**验收用例**

- 支付和取消并发，只有一个状态迁移成功。
- 超时消息重复到达，库存只回补一次。
- 取消已支付订单不会回库存。
- 退款不回库存、不释放额度。
- 旧订单可支付、使用、退款，但旧商品不恢复售卖。
- MQ 超时通知丢失时，数据库扫描仍能取消过期订单。

### 阶段 7：结果查询与前端闭环

- [ ] 新增按订单号查询本人建单结果的接口。
- [ ] 前端发送并保存本次购买请求键。
- [ ] 重试复用请求键，主动再购买创建新键。
- [ ] 排队期间轮询 MySQL 结果接口。
- [ ] 查到订单后进入真实支付页面。
- [ ] 倒计时使用订单 `payDeadline`。
- [ ] 去除写死商品、订单号和模拟支付成功跳转。

**验收用例**

- 结果查询不调用 Redis 或 ES。
- 不可查询其他用户订单。
- 排队响应不直接进入支付成功页面。
- 页面刷新可继续查询已保存订单号。
- 首次响应丢失后重试仍获取原订单号。
- 商品隐藏、回补恢复与已确认规则一致。

- [ ] 更新需求、接口、配置、部署和测试文档。

## 十、最终验收清单

- [ ] 数据库没有新增表、字段或索引。
- [ ] 所有新订单采用雪花 ID，历史订单不变。
